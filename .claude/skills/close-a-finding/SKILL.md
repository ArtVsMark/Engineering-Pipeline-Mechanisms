# Находка разбирается с премисы, а не с починки

> **Читатель:** окно, берущее находку внешнего взгляда.

## Зачем это существует

Находка приходит как утверждение о дереве, и читается как факт. Но взгляд
смотрит **дифф изменения**, а не нынешнюю общую ветку: он законно находит то,
что починили после слияния. Починка по непроверенной премисе — работа впустую, и
хуже того, она **переписывает уже верный код**
([044](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/blob/main/rules/ru/044-check-the-premise-before-fixing.md)).

**Замер 16.09.2026.** Поздний взгляд на #333 объявил дефект
`resolutions_in_all теряет метку при столкновении отпечатков`. Дефект был
настоящий — и **починен двумя днями раньше** изменением #348. Взгляд смотрел
дифф #333, где код ещё был прежним. Заметил это человек, а не механизм.

Второй замер того же дня: два риска взгляда — `6e80ae9` и `968f258` — говорили
об одном: работа режется **по числу находок одного захода**, а не по тому, что
они трогают.

## Что сделать

**1. Проверить премису на НЫНЕШНЕЙ общей ветке.**

```bash
git fetch origin main && git log --oneline -6 -- <файл из находки>
sed -n '<строки>p' <файл>            # прочитать код сегодня
```

Если код уже иной — находка **разобрана**, и снимать её надо с причиной, а не
чинить заново:

```
Разобрано: <отпечаток> — починено изменением #NNN, взгляд смотрел прежний дифф
```

**2. Проверить, не об одном ли они.** Один дефект взгляд называет дважды разными
словами — из разных заходов, с разными отпечатками. Признак: пересекаются файл и
строка либо совпадает предмет. Тогда снимаются **оба одной работой**, и это
говорится прямо.

**3. Резать работу по ПЕРЕСЕЧЕНИЮ ФАЙЛОВ, а не по числу находок.** Две находки,
трогающие один файл, — одно изменение; пять находок в пяти файлах — пять
изменений. Число находок одного захода — свойство ревьюера, а не работы
([133](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/blob/main/rules/ru/133-file-overlap-sets-the-boundary.md)).

Новая логика при этом идёт **отдельным изменением** от текстовых правок, даже
если они в одном файле: решение 008. Смешанное изменение нечем откатить по
частям.

**4. Вес читается, а не пересчитывается.** `дефект` — поведение расходится с
обещанным, `риск` — сломается при названном условии, `замечание` — текст и
единообразие. Разбирают в этом порядке; понизить вес по ходу нельзя — оценку
ставит не тот, кто чинит
([086](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/blob/main/rules/ru/086-the-finder-does-not-grade-the-finding.md)).

**5. Снять строкой в теле изменения, а не жестом.**

```
Разобрано: abc1234
Разобрано: def5678, 21e7c8e — один дефект, названный дважды
```

Снятие едет **вместе с работой**: отдельный жест забывают. Механизм уносит
запись следующим заходом уборки.

**6. Риск, на который нет механизма, снимается с ПРИЧИНОЙ, а не молча.** Если
находка про практику («не смешивайте в одном изменении»), а гейта на неё нет и
не предвидится, — так и написать: принято, держится чтением, мерка субъективна.
Молчаливое снятие неотличимо от «надоело»
([154](https://github.com/ArtVsMark/Engineering-Incidents-Playbook/blob/main/rules/ru/154-none-must-name-its-reason.md)).

## Чего этот навык НЕ делает

- **Не закрывает задачу реестра.** Записи снимает механизм по отпечатку, задачу
  закрывает человек: механизм не знает, разобрано или надоело.
- **Не спорит с весом.** Если находка кажется неверной — это снятие с причиной,
  а не понижение веса.
- **Не краснеет.** Вызывается, а не срабатывает (002).
